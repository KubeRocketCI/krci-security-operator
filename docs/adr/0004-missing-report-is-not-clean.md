# A missing report is not clean

The operator closes a runtime test only when its stable workload is gone, its container is no longer in the pod template, or its namespace is gone or excluded. A missing report never closes a test. Trivy Operator deletes a VulnerabilityReport on TTL expiry (24 h by default) and writes it again after the next scan, skips images it excludes, and keeps the old report after a failed scan, so the absence of a report means "not scanned". An empty report means "clean", and its reimport closes the findings through DefectDojo.

A test is closed with one reimport of an empty report into the test by ID (`close_old_findings=true`, the service of one active finding of the test, the version of the test resent, no tags, no `scan_date`, no `build_id`). DefectDojo mitigates every finding of that service in the one request, where one request per finding takes about 0.5 s each (a test of 1,700 findings: about 15 minutes against 10 s). The answer holds the number of active findings of the whole test; findings of another service stay active in it, so the close repeats with the service of the next active finding, for at most 5 services (a test written by an earlier version has findings without a service next to findings with one), and closes what remains one by one. A test that DefectDojo refuses to reimport (a 4xx other than authentication, throttling, timeout and conflict) or whose reimport fails with a 5xx, a transport error or a client timeout is closed one by one entirely, in the same call: a close that kills the DefectDojo worker every time would otherwise never end. A 409 (another import into the test is in progress), 401, 403, 408 and 429 are returned, and the next pass repeats the close. The report is one constant document without results (`{"metadata":{"labels":{}},"report":{"vulnerabilities":[]}}`), the same for both report kinds because the parser reads the labels and the result list, not the kind. It is never built from a Trivy report, so no upload of a report reaches this path.

## Considered Options

- Close a test when no current report is listed (the first version). Rejected: every TTL rescan closed and then reactivated all findings of the workload.
- Close after a grace period. Rejected: a timer adds state and still closes findings that are only unscanned.
- Close one finding per request (`POST findings/<id>/close/`). Kept as the fallback only: it takes minutes for a large test, and DefectDojo has no bulk close in API v2 or v3.
- Derive the service of the close from the title of the test. Rejected: the title holds the kind in lower case and a shortened workload and container, and the service holds the canonical kind and a different shortening, so one cannot be computed from the other for every test, and tests of earlier versions carry what those versions wrote. The service is read from one active finding of the test instead.

## Consequences

- The reimport mitigates the findings of its service that are not active as well: a false positive and an out of scope finding get mitigated and keep their flags, and a finding the user accepted as a risk is mitigated and loses its risk acceptance (DefectDojo removes it on every reimport that mitigates the finding). Closing one by one never touched them. A test whose findings are all inactive is not reimported and stays as it is.
- The reimport writes a note on each finding it mitigates and one import history entry with the number closed; closing one by one wrote neither.
- The reimport writes the version of the test, an empty one when none is sent, so the close resends the version of the listed test. It writes an empty `build_id` at its end, after the findings are mitigated, so the close clears a `build_id` of the listed test with an update before the reimport (ADR 0006); a test without one gets no update.
- The close is a single request that holds a DefectDojo worker until all findings are mitigated, and DefectDojo reads the findings of the service into memory. A close that times out leaves its result unknown; the operator closes the test one by one in the same call, and a repeat finds nothing left to mitigate.
- A service that matches no finding closes nothing and DefectDojo still answers 201; the active count of the answer is what the operator trusts, and findings that stay active are closed one by one.
- The reimport moves the `target_end` of the test, and of a CI/CD engagement, to today, and sends one `scan_added` notification per test where one request per finding sends one `finding_closed` each.
- A container whose image Trivy Operator excludes keeps its last test open.
- A workload scaled to zero is not gone: its tests stay open until the workload is deleted.
- A ReplicaSet whose controller is not a Deployment (an Argo Rollouts Rollout, a custom controller) is its own workload: each old ReplicaSet kept at zero replicas has its own test, and its findings stay active until the ReplicaSet is deleted.
- A broken report (`GLOSSARY.md`) is never uploaded, because DefectDojo would read it as empty and close every finding of the test. A report is broken when it has no resource kind or name, no container name label, no `report` block, or no result list (`report.vulnerabilities` for a VulnerabilityReport, `report.secrets` for an ExposedSecretReport). Trivy Operator always writes the list, also when it is empty.
- A failed upload gives the operator no right to close that test; the result in DefectDojo is unknown (DefectDojo does not apply a reimport as one transaction), so the operator retries the upload. The other tests of the namespace are still closed by these rules.
