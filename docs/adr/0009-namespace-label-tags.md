# Copy allowlisted namespace labels into tags

The installer lists Namespace label keys in `namespaceLabelTags` (environment variable `NAMESPACE_LABEL_TAGS`). For each listed key that a namespace has, the operator writes the tag `k8s-ns-label.<key>:<value>` on the namespace product and on every runtime test of the namespace. The list is empty by default, and then the operator writes the same requests and product tags as before, except that it removes a tag with the owned prefix `k8s-ns-label.`. The operator names no label itself, so it still reads no KubeRocketCI data (ADR 0001). We chose this because two needs remain after ADR 0001 and 0002. A DefectDojo user needs proof on the data itself of who owns a namespace: a KubeRocketCI Stage can name a namespace whose owner nothing verifies, as on OpenShift or for in-cluster Stages under Capsule, and the platform labels the namespaces of Stages with `app.edp.epam.com/tenant=<tenant namespace>`. DefectDojo users also cannot tell the namespaces of environments from the namespaces of add-ons. A tag of the installer's choice answers both, for KubeRocketCI and for any other platform that labels its namespaces.

## Considered Options

- Copy the labels of the workloads. Rejected: the developers of a namespace write them, so a tag taken from them proves nothing about the owner and can be forged.
- Read the tenant from KubeRocketCI: the label `app.edp.epam.com/tenant` by name, or the Stage resources. Rejected by ADR 0001: the operator would depend on KubeRocketCI and write nothing on a cluster without it. The listed key reaches the same result, and the operator does not know it.
- Copy every label of the namespace. Rejected: labels of unrelated tooling (the Pod Security labels, `kubernetes.io/metadata.name`) would become tags on the product and on every test, and any label change would upload every report of the namespace again. The list keeps the tags, and the uploads they cause, to the ones the installer chose.
- Tag the product only. Rejected: findings are filtered by the tags of their test (ADR 0003), so a reader who starts from tests or findings would need a second lookup.
- Patch the tags of the tests without a reimport, to avoid the upload. Rejected: a reimport replaces the tags of the test with the tags of its request (ADR 0003), so the label tags must be in every request, and so in the upload marker (ADR 0006).

## Consequences

- The tag is `k8s-ns-label.<key>:<value>`. The key is in lower case, which is how DefectDojo stores the tags of a test; it keeps the case of a product tag, so the operator writes lower case on both, and the two agree. The value is made tag-safe and shortened as the value of every other tag (`docs/trivy.md`, Length limits). A key that the namespace lacks, and a label with an empty value, give no tag.
- A label value of a Namespace has at most 63 characters, so only a long key makes a tag reach the 255 characters of DefectDojo. The operator does not start when the tag of a key could exceed them; the limit on the key length is in `docs/trivy.md`.
- The setting is validated like the other settings: a key that is not a valid Kubernetes label key fails the start with a message that names the variable. Two keys that give the same tag key, a repeated key or keys that differ in case only, also fail, because `REPORT_KINDS` ignores a repeat but a repeated label key is more likely a typo than a wish. The number of keys has no bound, because no list of the operator has one.
- The operator owns the prefix `k8s-ns-label.` on every namespace product, also while the list is empty. Each pass over an imported namespace adds the tags of its labels, corrects a wrong value, removes a tag of a label that is gone or whose key left the list, and keeps every other tag, as it does for `k8s-cluster` and `k8s-namespace`. A tag with that prefix that a person wrote is removed from the product of a namespace the operator imports. Disabling the setting therefore removes the tags from the products on the next pass.
- The operator does not follow the labels of a namespace that is gone, terminating or excluded. Its product keeps the label tags of the listed keys that it already has, because the operator cannot tell the value it wrote from one a person wrote, and loses the label tags of keys that are no longer listed, all of them while no key is listed.
- A change of a listed label reaches DefectDojo on the next pass, not on the next resync: the Namespace watch enqueues the namespace when its label tags change, and ignores every other update. The tests of current reports are uploaded again with the new tags; a closed test keeps the label tags of its last upload. The sweep also wakes a live namespace whose product has wrong label tags, so a product edited by hand is repaired.
- The label tags are part of the tag list of every reimport, so they are part of the upload marker. Enabling the setting, changing the list, and changing the value of a listed label give every test of the affected namespace another marker, and every report of a labelled namespace is uploaded once, as for any other change of the tags. Disabling the setting uploads the reports once more, and their marker is again the one without label tags. The request format version is not bumped: it covers what the marker does not hold, and the tags are in it.
- A tag value is in lower case, so the labels `Prod` and `prod` give one tag, and the original case is not recoverable from DefectDojo. A reader compares values in lower case.
- The tag is as trustworthy as the right to edit the Namespace. The operator copies what the label says and verifies nothing, so a reader that needs a proof must trust who may label namespaces.
- The ClusterRole is unchanged: the operator already reads the Namespaces.
